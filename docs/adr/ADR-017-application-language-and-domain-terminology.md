# ADR-017：应用语言与领域术语显示边界

- 状态：已接受
- 日期：2026-07-15
- 范围：应用偏好、前端国际化、用户可见领域名称

## 背景

ForgeOS 的内部模型使用 Project、Snapshot、Session、Evidence、Context Export 等稳定的英文领域名称。这些名称适合代码、数据库和协议，却提高了中文用户第一次使用时的理解成本。此前部分页面标题、导航、按钮和错误信息直接暴露内部术语，且日期格式固定为中文，无法形成完整一致的双语界面。

语言切换还必须与研发事实严格分离。用户填写的项目内容、Git/GitHub 原文、AI 回复、既有 Context Pack 和 MCP 输出都可能参与哈希、审计或外部协作，不能因为界面语言改变而被翻译或重写。

## 候选方案

1. 继续在组件内维护中英文字符串：改动较小，但容易遗漏，无法检查资源完整性，也会继续产生混合语言页面。
2. 重命名 Rust Entity、数据库字段和枚举：可以统一名词，但会破坏迁移、协议兼容和既有研发事实，风险不可接受。
3. 建立独立的应用偏好与前端显示层：内部模型保持不变，只在用户界面翻译页面结构、状态和操作，并允许中文用户按需查看英文术语说明。

## 决策

选择方案三。

- 使用 SQLite 单例表 `app_preferences` 保存本机应用语言和术语提示偏好，不与 Workspace 或 Project 绑定。
- `language_mode` 支持 `system`、`zh-CN`、`en-US`；系统语言以 `zh` 开头时解析为简体中文，其余系统语言回退英文。
- Rust Domain、数据库表、字段、枚举、IPC 业务结构和现有 URL 保持不变。
- 前端使用静态、随应用发布的 `i18next` 资源；翻译键采用稳定语义键，中英文资源必须具有相同键集合。
- 默认中文界面使用通俗名称，例如“当前状态”“开发记录”“项目资料”“AI 协作”。内部英文术语只在中文且用户开启术语提示时出现在页面标题附近。
- 用户内容、外部内容、AI 内容、Context Pack 和 MCP 返回不经过界面翻译。
- IPC 错误根据稳定错误码显示通俗标题和解决建议；原始错误与技术代码进入可折叠的技术详情。

## 优点

- 中文用户无需理解内部架构名即可完成主要流程。
- 语言设置在重启后保持，并与具体工作区和项目解耦。
- 领域模型、迁移历史、哈希和外部协议完全兼容。
- 新增文案有统一入口，可以自动检查双语资源是否缺键。
- 专业用户仍可选择显示英文术语，方便对照技术文档。

## 缺点

- 所有用户可见文本都必须持续维护两套语言资源。
- 旧组件中的硬编码文案需要逐步迁移并由测试防止回归。
- 外部原文可能与当前界面语言不同，但这是保护事实完整性的必要结果。

## 长期影响

- 新页面必须先定义通俗的用户用途、主要操作和稳定翻译键，再实现界面。
- 新数据库枚举必须同时进入中央显示字典，但不得为了显示目的修改存储值。
- 后续增加语言时复用同一应用偏好与资源契约，不引入自动翻译服务。
- Context Pack、MCP 和证据链继续使用原始内容；界面语言永远不是研发事实的一部分。
